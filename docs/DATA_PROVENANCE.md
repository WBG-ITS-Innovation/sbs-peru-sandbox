# Data provenance

Every complaint record committed to this repository at `HEAD` is generated by a
seeded script that reads no external data, so a clone can reproduce each
committed artifact byte-for-byte and verify that rather than take it on trust.
No SBS production data, no real consumer complaints, and no personally
identifiable information are included.

> The full account — what generates which artifact, what is regulatory
> vocabulary rather than data, which data-quality faults are deliberate, and
> what changed on 2026-08-14 and why — is in
> [DATA_PROVENANCE.md](../DATA_PROVENANCE.md) at the repository root. This page
> is the short version.

## How the data is produced

- **Corpus generator:** `scripts/generate-synthetic-corpus.py`, seeded and
  deterministic — the same seed reproduces the same corpus byte-for-byte.
- **Templates:** `data/synthetic-corpus-templates.yaml` defines the narrative
  and field templates the generator draws from.
- **Committed golden sample:** `data/synthetic-corpus-golden/` holds 200 rows
  for each of three fictional demo institutions, each with a manifest recording
  row counts, reporting period, schema version, and a SHA-256 checksum of the
  CSV. Regenerate with `make corpus-golden`.
- **Full corpus:** `make corpus` regenerates the ~10k-row corpus locally; it is
  gitignored and never committed.
- **App fixtures:** `scripts/build_rr1_fixture.py` generates the RR1 reporting
  fixture behind `/app/rr1`, and `scripts/build_journey_fixtures.py` generates
  the 80 complaint records behind the FI inbox and the live-ingestion ticker.
  Both are seeded and byte-stable, and neither reads any input data.
- **Fidelity tiers:** ADR 0036 documents how synthetic records approximate the
  statistical shape of the Annex 1-A schema — 27 fields under Res. SBS N°
  04036-2022 (23 base + 4 conditional bancaseguros), of which the API
  implements a curated 15-field subset per
  [ADR 0026](adr/0026-anexo-1a-curated-subset.md) — without deriving from real
  submissions.
- **Enforced:** `tests/cleanup/test_no_real_entities.py` fails if a real
  financial institution is named in any committed data fixture or generator.

## Fictional identities

Demo institutions are invented, use placeholder registration codes, and are
named consistently across the seed data and the app fixtures — *Banco Nuevo
Horizonte del Perú*, *Cooperativa de Ahorro Coopac Andes Centro*, *Financiera
Surandina del Perú*. Person-like names in the data are assembled from pools of
given names and surnames, one draw per row: a combination, not a person. Demo
personas and login accounts use role names ("Conduct Supervisor (Demo)") and
addresses under `sandbox.example.com`, a domain reserved by RFC 2606 for
documentation and testing, making their fictional nature unambiguous.

## Bundling rationale

The synthetic golden sample and the app fixtures are committed deliberately so
the sandbox runs end-to-end on a fresh clone with no external data dependency.

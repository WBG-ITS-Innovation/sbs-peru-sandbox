# ADR 0018 — SBOM format: CycloneDX JSON via syft

- **Status:** Accepted
- **Date:** 2026-05-16
- **Target prompt / Part:** Prompt 2 / Part 1 (format locked); implementation in Part 9
- **Supersedes:** —
- **Superseded by:** —

## Context

The handoff package promised in PLAN.md Part 9 includes a Software Bill of Materials (SBOM). The implementation — a GitHub Actions workflow that produces and attaches an SBOM to each release — belongs in Part 9, with the rest of the production-readiness work. The **format** decision should be locked now, while the supply-chain context is fresh and the upstream choice (CycloneDX vs SPDX) does not yet bind anything.

Two practical SBOM formats are in active use:

- **CycloneDX** (OWASP project). JSON or XML. Strong tooling ecosystem (OWASP Dependency-Track, OpenSSF Scorecard). Used by default in Anchore's `syft` and by Sigstore for release-artifact attestations.
- **SPDX** (Linux Foundation). Tag-value, JSON, YAML, or RDF. Strong license-metadata coverage. Default in some Red Hat and Google tooling.

CISA's "Minimum Elements for a Software Bill of Materials" (2021) is format-neutral. The German BSI's TR-03183 also accepts both. The decision boils down to which format the *downstream consumers* (the inheriting vendor, an SBS auditor, a security scanner in the SBS environment) can ingest with the least friction.

## Decision

SBOMs are produced in **CycloneDX JSON format**, generated by Anchore's **`syft`**.

- One SBOM per built image (Part 9, once Dockerfiles exist).
- One SBOM per Standards Pack release (Part 11).
- SBOMs are attached as release assets and published as an OCI artifact alongside each tagged release.

The Part 9 GitHub Actions workflow that produces this is out of scope for this prompt — only the format choice is locked here.

## Precedent

See [docs/research/supply-chain-precedents.md, §3 — "SBOM format"](../research/supply-chain-precedents.md#3-sbom-format). Comparators cited: CISA "Minimum Elements for a Software Bill of Materials" (2021, format-neutral), Anchore `syft` (defaults to CycloneDX), OWASP Dependency-Track (CycloneDX-native), OpenSSF Scorecard checks (consume CycloneDX), Sigstore release-attestation tooling (defaults to CycloneDX), and the German BSI TR-03183 (recognises both formats). CycloneDX JSON via `syft` is the most-supported pipeline shape — Trivy, Grype, Dependency-Track, and OpenSSF Scorecard all consume it without an adapter.

## Divergence

No material divergence. SPDX is a defensible alternative; CycloneDX wins on tooling ecosystem alignment for this stack. The platform's downstream consumers (vendor, SBS audit, third-party scanners) will all accept CycloneDX without a converter.

## Consequences

- Part 9 must produce CycloneDX JSON SBOMs; the workflow ADR (separate, in Part 9) inherits this format choice.
- Anchore `syft` becomes a build-time dependency. It is a single static binary; no runtime dependency on the application.
- If a downstream consumer requires SPDX, `syft` can emit SPDX from the same source — but the canonical artifact is CycloneDX.
- License-compliance scanning (Part 9, separate ADR) reads from the same SBOM.

## Flagged for cross-review

None for the format choice. The workflow implementation ADR (Part 9) will be a separate cross-review trigger.

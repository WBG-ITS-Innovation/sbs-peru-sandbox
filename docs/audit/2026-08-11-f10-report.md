### The remaining index churn — one paragraph, as scoped

Four indexes are created by migrations but never declared on their model, so
`Base.metadata` has no claim on them and autogenerate reports each as removed:

```
$ uv run python -c "...check declared indexes per table..."

ix_institution_certificates_cn              in metadata=False

ix_oauth_clients_institution_id             in metadata=False
   institution_certificates declares: []
   oauth_clients declares: []
```

They come from `20260519_0001_auth_chain.py` and
`20260527_0001_flag_unknown_taxonomy.py`. This is the same *class* of drift as the
orphan tables — DB objects with no metadata counterpart — but at index level, and it
is out of scope here: closing it means either adding `Index(...)` declarations to
four models or renaming indexes across shipped migrations, and the instruction
explicitly rules the latter out. **Practical consequence for a maintainer:
autogenerate output on this repo is no longer capable of dropping a table, but it
still emits four spurious `drop_index` lines, so a generated migration must still be
read before it is applied.** Tracked here; no index was renamed.

## Newly discovered — P0-class, pre-existing, NOT fixed here

**`MockProvider`'s script cursor never resets, so only the first complaint per agent
per process gets a real agent run.**

Found while checking why the `stage-h-full` Tier-2 triage row looked thin. It had
**zero** tool calls where Tier 1 had three:

```
$ psql -tAc "select jsonb_array_length(tool_calls), jsonb_pretty(tool_calls)
             from agent_runs where complaint_id='COP-2026-459684' and agent_name='triage';"
0|[
]

$ psql -x -c "select jsonb_pretty(final_output) from agent_runs where complaint_id='COP-2026-459684' ...;"
     "priority": "low",
     "route_to": "info-only",
     "classification": { "label": "other", "model_id": null, "confidence": 0.55 },
     "reasoning_summary": ""
```

Not a registry problem — the worker has all ten tools:

```
$ docker exec sbs-worker ... python -c "from sbs_api.agents.tools.base import list_tools; ..."
registry before agents import: 10
registry after triage import : 10
```

The cause is in `api/sbs_api/agents/providers/mock.py`: `MockProvider` keeps a
per-agent cursor (`self._cursors`) that advances on every `complete()` call and is
reset only by an explicit `reset()` nobody calls. `get_provider()` caches one
instance per process. Past the end of the script it returns `{"text": ""}` — no tool
calls at all.

Two identical Tier-1 submissions, back to back, same API process:

```
--- BCO-2026-941883 ---   (first in this process)
triage         | tools=3 | label=undisclosed-fees-credit | conf=0.82
investigation  | tools=4 | label=- | conf=-
synthesis      | tools=2 | label=- | conf=-
cross-source-correlator | tools=2 | label=- | conf=-

--- BCO-2026-341940 ---   (second)
triage         | tools=0 | label=other | conf=0.55
```

**Why this matters.** The default posture is `on_prem`, which falls back to
`MockProvider` whenever no vLLM answers — the situation on every machine in this
engagement. Under that posture the agent layer produces a real result for the first
complaint a process sees and a degenerate one for every complaint after it.

**It is pre-existing, not an F10 or P0-run regression** — `MockProvider` has behaved
this way since Part 12. What the P0 run changed is its consequence: before `ed2e812`
the chain ran once per short-lived script invocation, so the cursor never mattered;
now it runs inside long-lived processes (the API and the worker) on every ingested
complaint.

**Correction to the P0 fix report.** Its F2 and F8 evidence — including "the chain
now runs to depth on a real Tier-1 complaint" — was measured on the *first* complaint
after a process start and is accurate only for that case. It overstates steady-state
behaviour. That report is closed and was not edited; this paragraph is the
correction.

**Not fixed here** — out of F10's scope, and it touches provider semantics that a
number of tests depend on. Recommended fix, for a maintainer to weigh: key the
cursor by `(agent_name, complaint_id)` rather than `agent_name`, so each complaint
replays the script from the top; or have the orchestrator call `reset()` per run.
Either is small, but both change behaviour the existing provider tests assert on, so
it wants its own commit and its own review.

**Gate blind spot this exposes.** `stage-h-full` submits exactly one complaint per
tier, so it cannot see this class of bug. A second submission per tier, asserting a
non-empty `tool_calls` array, would catch it. Worth adding when the fix lands.

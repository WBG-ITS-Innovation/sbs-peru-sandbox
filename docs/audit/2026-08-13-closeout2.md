## 0. Environment caveats, stated up front

Two facts about the machine this ran on, because they qualify every result
below.

### 0.1 `uv` is not installed on this host

The README lists `uv` as a prerequisite, and the shipped scripts invoke
`uv run`. It is absent here — not on `PATH`, not in a login shell, not
anywhere on the filesystem:

```
$ zsh -lc 'which uv; uv --version'
uv not found
zsh:1: command not found: uv
```

The project venv at `.venv/` is intact and complete (alembic, pytest, openai,
httpx, asyncpg, arq, fastapi all import). Interestingly `uv`'s managed Python
is still present — tracebacks below resolve through
`~/.local/share/uv/python/cpython-3.12.13-macos-aarch64-none/` — so the binary
appears to have been removed while its data directory survived.

Rather than edit the shipped scripts (which would invalidate "run as
shipped"), a shim was placed on `PATH` for this session only, in the
scratchpad, mapping `uv run <cmd>` to `.venv/bin/<cmd>`:

```sh
case "$1" in
  run) shift; ...; exec "$VENV/bin/$cmd" "$@" ;;
```

**What this means for the results.** Every script ran byte-unmodified and every
assertion below is real. But real `uv run` also performs a dependency sync
against `uv.lock` before executing, and the shim does not. So these runs prove
the code works against the venv as it currently stands; they do not prove the
venv matches `uv.lock`. Anyone reproducing this should install `uv` first, and
should treat a lockfile-drift failure as unexplored territory rather than a
regression.

### 0.2 The stack was warm and was deliberately cooled

Before starting, `:3000` (cockpit dev server), `:8443` and `:8000` (two API
processes) were live, alongside compose postgres/redis/keycloak/worker/
webhook-listener. The two API processes had started at 12:10, i.e. **before**
the base commit landed at 15:15, so they were running pre-healthcheck code. All
three were stopped and restarted from cold for the walk in §1.3.

### D.4 — the gate

`tests/cleanup/test_no_real_entities.py`. Nothing in the secret-scanner stack
could have caught either blocker — gitleaks and detect-secrets look for
credentials, and third-party data is not a credential. Both sat in tracked
files through a clean gitleaks run over 260 commits.

Denylist of 7 brand names and the 45 institution rows of the RR1 Empresa sheet,
over tracked data fixtures *and the scripts that generate them* — a generator
holding a real name puts it back on the next regeneration, which is how B2
happened. The five segment heading rows are excluded: they are regulatory
classes of entity, not entities.

Two matching strategies, because one does not fit both. Brands match
case-insensitively on word boundaries. Workbook labels match case-sensitively
and verbatim — `ALTERNATIVA` and `NACION` are real institution labels *and*
ordinary Spanish, and a gate that fires on ordinary Spanish gets switched off.
This follows the sweep's own methodology note that `git grep -IlE "\b(…)\b"`
fails silently; the test uses Python's `re`, which honours `\b`.

Negative controls, since a containment gate that cannot fail is worse than no
gate: all 52 names detected when planted (brands in three casings); the whole
read-and-match path exercised against a planted file on disk, not just the
matchers; innocuous Spanish and all five segment classes asserted not to trip
it; the scan scope asserted to contain the six files it exists for, so a glob
matching nothing cannot pass silently; `git ls-files` failure asserts rather
than skips.

Beyond the denylist, two closed-set checks: every Empresa row must be one of
the generator's own invented names, and the journey fixture's entity pool must
be fictional. Stronger than absence — the generators hold the closed set of
names they may emit, so the fixtures are checked against what they must say
rather than a list of everything they must not.

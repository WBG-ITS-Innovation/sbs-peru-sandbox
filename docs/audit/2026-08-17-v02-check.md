### F1 — `stage-h-full` fails on a cold stack when the worker is started per the docs

**This is the one finding that would bite a new operator, and it reproduced on
the first run before I knew to look for it.**

`HANDOVER-NOTES.md` ("Operating the stack") and `PRODUCTION.md` §7 both give
this command for bringing up the worker with the agent pipeline:

```bash
SBS_API_AGENTS_PIPELINE_ENABLED=true docker compose up -d --force-recreate worker
```

I ran it verbatim. `docker-compose.yaml` sets
`SBS_API_MODEL_PROVIDER: "${SBS_API_MODEL_PROVIDER:-on_prem}"`, so the worker
came up on `on_prem` with no vLLM anywhere. Tier 1 passed (four agents,
`provider=replay`, from the host API). Tier 2 failed:

```
[10:18:40] tier2: asserting row 1/2 (COP-2026-976321)
[10:19:40] FAIL: tier2: no triage agent_run for COP-2026-976321 within 60s
  contract half: PASS
  live half:     FAIL
FAIL: stage-h-full: contract_rc=0 live_rc=1
```

The worker log gives the cause exactly once per complaint, at `error` level:

```json
{"complaint_id": "COP-2026-976321", "tier": "tier2",
 "error_type": "ProviderUnavailableError",
 "error": "provider 'on_prem' unavailable: vLLM unreachable at
           http://localhost:8001/v1 ... ConnectError('All connection attempts failed')",
 "event": "agents.dispatch.failed"}
```

Recreating the worker with the provider set makes the gate green, live half
included, with no other change:

```bash
SBS_API_AGENTS_PIPELINE_ENABLED=true SBS_API_MODEL_PROVIDER=replay \
  docker compose up -d --force-recreate worker
# → stage-h-full: PASS   (contract half: PASS   live half: PASS)
```

**The gate is sound and the code is correct.** What is wrong is the documented
invocation: it is missing `SBS_API_MODEL_PROVIDER=replay`. This matters more
than a normal doc nit because `OPERATOR-CHECKLIST.md` makes "all ten gates
green, including the `-full` variants" a go-live gate — so an operator
following the repository's own instructions hits a red gate on a correct build.

**F1b — and the paragraph that would mislead them while debugging it.**
`PRODUCTION.md` §7 says of `on_prem` that it "refuses to boot without one when
the pipeline is enabled (`provider.healthcheck.failed`)". That is true of the
**API** process, whose boot healthcheck arms the canary — and false of the
**worker**, which is what §7 is about. The worker boots cleanly, reports
`Starting worker for 2 functions`, ingests batches normally, and fails per
complaint after the fact. §7's rule 1 already makes exactly this point about the
pipeline flag — "Nothing looks broken; the analysis is simply absent" — and the
provider has the same failure signature but is described as boot-fatal.

Fix: add the variable to the command in both files, and correct the one
sentence. Two lines.

## 2. P1 — ReDoS in the redaction engine, checked independently

The fix is exactly two pattern lines, `\s*[:.-]?\s*` → `\s{0,4}[:.-]?\s{0,4}`
via a shared `_ID_SEPARATOR`.

### Valid DNI/RUC redaction is byte-identical

There is no committed golden checksum for redaction output — the "golden PII
bundle" is an inline test constant — so rather than assert byte-stability I
tested it differentially against the **actual pre-fix engine**, pulled from git
(`git show e5c9c06^:api/sbs_api/redaction/engine.py`) and loaded alongside the
current one in the same process.

Corpus: 111 cases. Valid 8-digit DNI and 11-digit RUC across twelve separator
forms each (none, space, `:`, `: `, ` : `, `.`, `. `, `-`, `- `, double-space,
tab, ` \t `), each in bare, in-sentence, lowercase and mid-clause positions;
bare digit runs with no keyword (the second alternation branch); four
wrong-length negatives (7, 9, 10, 12 digits); both kinds plus name, phone,
email, account and a Soles amount in one string; and adjacency/boundary stress.

The digest covers the full result, not just the text — every entity's kind,
rule_id, span, replacement, confidence and matched_value.

```
aggregate sha256 fixed : a95f1bfd95d95358f32bda713ce9b0c57cbce2b519e850f5f82010b4b619c1d5
aggregate sha256 old   : a95f1bfd95d95358f32bda713ce9b0c57cbce2b519e850f5f82010b4b619c1d5
identical              : True
per-case mismatches    : 0
```

The documented safe degradation was checked rather than taken on trust, and
behaves as documented — at 4 spaces the prefixed branch still fires, at 9 the
keyword falls outside the replaced span, and **the identifier is redacted
either way**:

```
spaces=4: fixed='<DNI_1>'              old='<DNI_1>'   digits_leaked=False
spaces=5: fixed='<DNI_1>'              old='<DNI_1>'   digits_leaked=False
spaces=9: fixed='DNI         <DNI_1>'  old='<DNI_1>'   digits_leaked=False
```

Same for RUC. No PII escapes in any case.

### The asymptotic claim, re-measured from scratch

One long whitespace run after the keyword, old pattern vs fixed:

```
  n spaces     OLD ms      x   FIXED ms      x
      2000      15.58      -      0.016      -
      4000      58.05    3.7      0.033    2.1
      8000     197.36    3.4      0.045    1.4
     16000     779.17    3.9      0.081    1.8
     32000    3086.30    4.0      0.157    2.0
```

4.0× per doubling before, 2.0× after — quadratic to linear, and a ~20,000×
constant-factor win at n=32,000. The fix is real and I did not have to take the
report's numbers for it.

### My own pathological inputs

The four committed cases are all "keyword, then whitespace, never any digits"
(`"DNI"+" "*200000+"!"` and `"DNI \t"*50000+"!"`, ×2 for RUC). I wrote eight
shapes of different mechanism — near-miss digit runs one short of the required
length (so the prefixed branch matches keyword *and* separator and only then
fails on the count); separator-saturated inputs that fill both bounded `\s{0,4}`
runs to exactly 4 plus the optional `[:.-]`, which is the worst case *for the
fix as written* rather than for the original bug; both kinds interleaved; a
single huge contiguous digit run; and digits followed by a word character so
the trailing `\b` fails after the digits are consumed.

Timed through the whole `redact()` pipeline at n, 2n, 4n:

| shape | chars (max) | ms (max) | growth over 4× |
|---|---|---|---|
| S1 near-miss 7-digit (DNI) | 624,000 | 96.53 | 3.5× |
| S1 near-miss 10-digit (RUC) | 768,000 | 131.83 | 3.9× |
| S2 separator-saturated DNI | 576,000 | 52.51 | 3.9× |
| S2 separator-saturated RUC | 576,000 | 65.01 | 5.0× |
| S3 both kinds interleaved | 1,248,000 | 224.75 | 4.1× |
| S5 non-boundary tail DNI | 624,000 | 91.89 | 3.9× |
| S5 non-boundary tail RUC | 768,000 | 130.89 | 3.6× |
| **S4 huge digit run** | **864,006** | **47,672.68** | **15.7×** |

Seven of eight are linear (≈4× over a 4× size increase) and complete in
double-digit ms on inputs 3–6× larger than the committed tests use. The two
patterns named in the alerts, timed in isolation on my worst shape, are
unambiguously linear: 4.35 → 8.65 → 17.22 ms across 288k → 576k → 1.15M chars.

**P1's own claim holds. But S4 found something else.**

### F2 — a second quadratic in `redact()`, which is not the one P1 fixed

S4 (`"RUC:  " + "9"*n`) takes 3.0 s at 216k chars, 12.1 s at 432k, 47.7 s at
864k — 15.7× per 4×, i.e. quadratic, in seconds not milliseconds. It is **not
regex backtracking**. Staging the pipeline by hand:

```
chars=216006  entities=11368   soles=22.8ms  DNI+RUC_patterns=2.1ms
                               account_detect=15.6ms  resolve_overlaps=2912.6ms
chars=432006  entities=22737   soles=46.8ms  DNI+RUC_patterns=5.1ms
                               account_detect=32.6ms  resolve_overlaps=11659.9ms
```

The cost is `_resolve_overlaps` at `api/sbs_api/redaction/engine.py:285`, which
compares every candidate against every already-kept entity:

```python
for ent in sorted_ents:
    if any(_ranges_overlap(ent.span, k.span) for k in kept):
```

`cProfile` on the 216k case: **64,610,028 calls** to `_ranges_overlap`, 8.4 s of
an 8.5 s total. Growth is 4.0× per doubling of entity count, textbook O(n²). A
long digit run is simply an efficient way to manufacture tens of thousands of
non-overlapping `pii_account` entities; a second shape (many Soles markers *and*
many account candidates) reproduces it at the same 4.0× rate, confirming the
driver is entity count rather than input shape.

**Reachability, which is what decides severity.** Both narrative surfaces cap
input at 8000 characters — `anexo_1a.description_text` (`min_length=10,
max_length=8000`) on the Tier-1/canonical path and `demo_ingestion.narrative`
(`max_length=8000`). At that cap the worst input I could construct costs
**7.40 ms**:

```
all digits (max account entities)    len=8000  entities=421   7.40 ms
digit run + soles markers            len=7998  entities=258   3.82 ms
spaced digits (14-digit groups)      len=7992  entities=327   4.03 ms
realistic Spanish narrative          len=5670  entities=180   1.61 ms
committed-test shape (whitespace)    len=8000  entities=  0   0.54 ms
```

So: **not exploitable through any documented API surface**, because the field
cap bounds it. It is worth recording anyway for three reasons. The cap is the
only thing containing it (8000 → 6.2 ms, 16k → 20 ms, 64k → 275 ms, 128k →
1.06 s, so raising the limit or adding an uncapped caller reintroduces a real
DoS). The one call site without an explicit cap is
`ingestion/social/runner.py:68`, which redacts adapter-fetched post text. And
the four committed pathological tests cannot ever catch a regression here — they
are digit-free, so they produce **zero** entities and never enter
`_resolve_overlaps` at all. The P1 test suite's `PATHOLOGICAL_BUDGET_MS` guard
protects the two fixed patterns and nothing else.

Not a merge blocker. A good next dependency-free hardening task, and one extra
test case (`"9" * 8000`) would pin it.

### F3 — the `model_provider = NULL` gap is not only historical

`OPERATOR-CHECKLIST.md:174-178`, `HANDOVER-NOTES.md` and `CHANGELOG.md:37` all
frame the gap the same way: rows **predating** migration `20260810_0001` have
`model_provider = NULL`, and reporting should "filter on
`model_provider IS NOT NULL` when provenance matters".

The live database disagrees:

```
 prov_null | count |  earliest  |   latest
-----------+-------+------------+------------
 f         | 10068 | 2026-08-10 | 2026-08-17
 t         |   246 | 2026-07-13 | 2026-08-17
```

NULL rows are still being written **today** — 5 in the last three days — and
they are not failures: `status` is `success` (202 rows) or `partial` (44), never
`failed`. I reproduced it with my own two submissions from minutes earlier:

```
 complaint_id     | agent_name                  | status  | model_provider
------------------+-----------------------------+---------+---------------
 BCO-2026-6755083 | live-ingestion-orchestrator | success |
 BCO-2026-8137192 | live-ingestion-orchestrator | partial |
 BCO-2026-8137192 | triage                      | success |
 BCO-2026-8137192 | investigation               | success |
 BCO-2026-8137192 | synthesis                   | success |
```

versus a canonical Tier-1 complaint from `stage-h-full` on the same stack:

```
 triage                  | success | replay | 3 tool calls
 investigation           | success | replay | 4 tool calls
 synthesis               | success | replay | 2 tool calls
 cross-source-correlator | success | replay | 2 tool calls
```

Two of the two `AgentRun(...)` constructions in the codebase omit
`model_provider`: `demo_ingestion/orchestrator.py:634` and
`agents/persistence.py:42` (the in-flight row, later filled by
`finish_agent_run`, which applies it only `if model_provider is not None`).
The demo/live-ingestion path — which is what the cockpit's `/app/ingestion`
loop and `scripts/sandbox_send.py` drive — records tool calls but no provider.
`finish_agent_run`'s own docstring is accurate about why ("Left None by agents
that make no model call"); the operator-facing documents are not.

**Why it matters beyond accuracy:** the mitigation the checklist prescribes
does not do what it says. Filtering `model_provider IS NOT NULL` silently drops
current, successful analysis rows from a live surface, not merely pre-migration
history — so an operator following the checklist under-counts today's runs. It
also sits awkwardly against `README.md`'s "**Every** agent run persists an
`agent_runs` row recording which provider *actually served* it".

The behaviour predates this train; the *newly shipped* checklist and changelog
wording is what makes it a P4 finding. Re-wording the item to name both causes
(pre-migration rows **and** runs that make no model call) is a doc fix, not a
code change.

## P1 — ReDoS in the redaction engine

CodeQL alerts #2 and #3 (`py/polynomial-redos`) at
`api/sbs_api/redaction/engine.py:177` and `:193` — the call sites of
`_DNI_PATTERN` and `_RUC_PATTERN`.

### Root cause

Both patterns separated the identifier keyword from its digits with
`\s*[:.-]?\s*`. Two adjacent unbounded `\s*` around an optional separator let
N whitespace characters be split between them N+1 ways, so a keyword followed
by a long whitespace run and no digits costs O(N²). Redaction runs on
attacker-influenced complaint narratives, making this reachable.

### Confirmed before fixing

Benchmarking all six engine patterns on adversarial input scaled 2×:

```
--- n=2000 ---            --- n=4000 ---           --- n=8000 ---           --- n=16000 ---
_DNI_PATTERN     17.50 ms  _DNI_PATTERN    51.14 ms  _DNI_PATTERN   189.96 ms  _DNI_PATTERN   754.90 ms
_RUC_PATTERN     16.22 ms  _RUC_PATTERN    47.95 ms  _RUC_PATTERN   189.72 ms  _RUC_PATTERN   758.86 ms
_SOLES_AMOUNT     0.10 ms  _SOLES_AMOUNT    0.16 ms  _SOLES_AMOUNT    0.31 ms  _SOLES_AMOUNT    0.60 ms
_PHONE_PATTERN    0.04 ms  _PHONE_PATTERN   0.07 ms  _PHONE_PATTERN   0.14 ms  _PHONE_PATTERN   0.28 ms
_EMAIL_PATTERN    0.02 ms  _EMAIL_PATTERN   0.03 ms  _EMAIL_PATTERN   0.07 ms  _EMAIL_PATTERN   0.14 ms
_ACCOUNT_PATTERN  0.05 ms  _ACCOUNT_PATTERN 0.08 ms  _ACCOUNT_PATTERN 0.15 ms  _ACCOUNT_PATTERN 0.32 ms
```

Doubling n quadruples DNI/RUC time — quadratic, as the alert says. **The other
four patterns are linear and needed no change**; this was checked rather than
assumed.

### Fix

A shared, bounded separator:

```python
_ID_SEPARATOR = r"\s{0,4}[:.-]?\s{0,4}"
```

Bounding each whitespace run makes the separator cost constant. The degradation
is safe and is pinned by a test: a keyword more than four spaces from its
digits no longer matches the *prefixed* branch, but the bare digit-run branch
(`\b(\d{8})\b` / `\b(\d{11})\b`) still fires, so **the identifier is redacted
either way** — only the keyword stays outside the replaced span. No PII escapes.

### Measured through `redact()`, vulnerable vs. fixed

Same probe, hard 30-second wall, whole pipeline not just the regex:

```
=== VULNERABLE (unbounded) ===          === FIXED (bounded) ===
  spaces=  12500      470.3 ms            spaces=  12500        1.0 ms
  spaces=  25000     1878.7 ms            spaces=  25000        1.8 ms
  !! KILLED at 30s wall — did not finish  spaces=  50000        3.5 ms
                                          spaces= 100000        7.0 ms
                                          spaces= 200000       13.6 ms
```

The vulnerable version did not finish 50,000 spaces within the remaining wall;
extrapolating the quadratic gives roughly two minutes for the 200,000-character
case the new test uses. The fixed version does it in 13.6 ms.

### Tests

- 8 DNI and 8 RUC separator forms (`DNI 123…`, `DNI: 123…`, `DNI:123…`,
  `DNI.123…`, `DNI-123…`, `DNI123…`, lowercase, double-space) — detection
  semantics unchanged.
- 3 wrong-length negatives (7-digit, 10-digit, 12-digit runs) — length

  describing a feature that is not there.

  collector's 4318 receiver with path `/v1/traces`. A gRPC endpoint (4317)
  exports nothing and fails silently. Verified in
  `observability/tracing.py`, which imports
  `opentelemetry.exporter.otlp.proto.http.trace_exporter`.
- **What does not ship:** no dashboards, no alert rules, no metrics exporter.

Env-var names and defaults were verified against `api/sbs_api/config.py` rather

### Two harness defects found and fixed during the run

Both are recorded because the first produced a plausible-looking finding that
was entirely an artefact:

1. **Complaint ids were not scoped to the run.** The first full run reported
   `errors 25 (2.08%)`, all HTTP 409 — exactly as many as the 25-request
   calibration run had made just before. The ids were derived from the sequence
   number alone, so the second run replayed the first run's ids and hit the
   uniqueness constraint. Ids now take a clock-derived base offset within the
   six-digit space the existing smoke scripts use. Re-run: 0 errors.

2. **Wave pacing used a one-second-resolution clock.** `date +%s` reported
   spurious "dispatch took 1s — offered rate not sustained" on roughly a fifth
   of waves, because a wave starting at x.9 and ending at y.0 measures as a
   full second. Pacing now uses a float clock and absolute per-wave deadlines,
   which also removes drift. A wave that genuinely misses its deadline is
   counted and warned about at the end.

The driver is deliberately **open-loop**: a closed-loop driver silently reduces
its own rate as latency rises and then reports a rate that was never offered.

### Framing

The script header, the closing banner, the JSON output, and `PRODUCTION.md` §8
all state that this is **sandbox-scale indicative only and not a load test**,
and enumerate why: client, API, Postgres and Redis share one machine; sandbox
data volumes so every index is small; a single API process rather than a
replica set; one client certificate so per-institution rate limiting is never
stressed; and a 60-second window too short for GC or connection churn to
appear. The caveat is embedded in the JSON so a number lifted out of context
carries its own disclaimer. The measured figures in `PRODUCTION.md` are
explicitly labelled as not a capacity claim.

## C3 — redaction before egress

`CloudProvider.complete()` passes every string in the outbound payload through
the redaction engine immediately before the request body is built: message
content, multimodal text parts, and the arguments of any replayed assistant tool
call. At the provider boundary rather than per call site, so a new agent or a
reordered prompt cannot reintroduce raw text. The agent's own message history is
not mutated, so a run behaves identically whichever provider serves it.

`cloud_inference_audit` (migration `20260817_0001`) records one row per outbound
call, **before** the request, because the audited event is the egress and not its
success. It stores no text, raw or redacted;
`test_audit_row_columns_cannot_hold_text` pins the column set. Its own
transaction, and it never fails the call — so
`cloud.egress.audit_failed` is the alert an operator needs before assuming row
count equals call count.

Migration is hand-written and additive. Verified mechanically:

```

-> DROP/ALTER in upgrade: []  OK (none)
downgrade(): ['drop_index', 'drop_index', 'drop_table']
```

`test_autogenerate_finds_no_table_level_drift` confirms the migration and the ORM

## C4 — two conditions, enforced independently

`cloud` is permitted for DIValeVale Pass-2 extraction — the most PII-dense prompt
the system builds — only when a recorded legal approval **and** an active egress
redaction layer are both present. Asymmetric for a reason: legal approval without
redaction sends raw narratives with permission; redaction without approval sends
off-premises without one.

Condition 2 is verified by exercising the code path, not by reading a setting:
`redaction_layer_active()` checks that the provider imports the sweep and that
calling it actually redacts a DNI. Unwire the sweep and the permission is
revoked. `test_redaction_layer_inactive_when_the_sweep_is_unwired` pins that
direction.

`test_cloud_provider_rejected` asserted unconditional rejection and was
**replaced deliberately** by three cases — refused without the approval, refused
without redaction, permitted with both — using a stub whose `complete()` raises,
proving the gate fires before any prompt is assembled.

### Three things the live run corrected, all folded back in

**1. Two of this leg's own assertions were wrong and passed for the wrong
reason.** The first version asserted that the egress sweep must have caught
something. That is an assertion that *upstream* redaction is failing — it would
pass loudest when the system was at its worst. On the first live run it passed
only because the sweep matched digit runs inside UUIDs in a tool result: an
`agent_run_id` of `12345678-af01-…` became `<DNI_1>-af01-…`, reported as
`pii_id: 2`. Removed. Entity counts are now reported and documented as an
**upper bound on PII, not a measurement**, and `{}` is documented as the correct
value. The vacuity guard was likewise re-anchored: it originally keyed on
redaction placeholders, which were themselves the UUID false positives.

**2. The narrative never egresses at all.** The agents' ten tools run locally
against Postgres and only their structured output reaches the model. Captured
from the live transport:

```
role=system  Eres TriageAgent del prototipo SupTech de la SBS…
role=user    Analiza el reclamo BCO-2026-998237 usando los tools disponibles.
role=tool    {"label": "undisclosed-fees-credit", "confidence": 0.82, …}
role=tool    {"errors": [], "warnings": [], "suggested": []}
role=tool    {"normalizations": [], "unknown_terms": []}
```

No narrative. So redaction at the boundary is a **backstop behind that design,
not the thing holding the line** — a materially different and stronger claim
than "we redact before sending", and the reason C6 states it that way. The leg
now *fails* if narrative text ever appears in an outbound payload, turning a
data-residency change into a deliberate decision instead of a drift.

**3. The 60 s poll budget failed a working system.** One investigation turn
against Azure measured 15 s and a full four-agent chain ~98 s, so the gate
reported `no triage agent_run … within 60s` while the chain was still running and
subsequently completed with `provider=cloud` on all three model-served agents.
Now 240 s when the provider is `cloud`, overridable via
`SBS_STAGE_H_POLL_TIMEOUT_S`.

Also fixed: widening the id list to five gave Tier 2 three rows instead of the
documented two and shared an index with the cloud leg. Back to `sfx[2:4]`.

## Not done, and why

- **UUID false positives in the egress sweep.** An eight-digit run inside a UUID
  matches the bare-DNI branch, so tool results come back with mangled
  `agent_run_id` values and inflated entity counts. Over-redaction is the safe
  direction and no agent depends on quoting an internal id back, so this is
  documented in `egress.py` and left as a follow-up: masking UUID-shaped tokens
  before the sweep and restoring them after would fix it locally, without
  touching the shared engine's semantics. Deliberately not done in the same
  train that introduced the sweep.
- **`_resolve_overlaps` remains O(n²).** Pinned by tests at the 8000-character
  cap rather than rewritten. The O(n log n) sweep is described in the docstring
  for whoever needs unbounded input.
- **`SECURITY.md` cites a `0.1.0-handover` tag that does not exist** (check F4).
  Untouched — it is a one-line inconsistency in a file this train did not
  otherwise open.
- **The cloud leg has only ever run on synthetic data**, and `on_prem` still has
  no live vLLM behind it anywhere in this engagement.

- **Date:** 2026-05-19
- **Model:** gpt-5.4
- **Target:** docs-adr-003-123

## Summary

The ADRs are clear and internally linked. The split of identity (mTLS), authorisation (OAuth scopes), and request binding (HMAC) is sensible and matches established practice in Open Banking.

The main issues I see are not with the overall direction, but with parts of the contract that are either underspecified or likely to fail in production if implemented exactly as written:

1. **CN as the runtime identifier is a weak choice** and is hard to defend long term. ADR 0031 says the runtime reads CN only and reserves SAN for later (`0031`, Decision, “Cert is the institution identity”). That is a dated pattern. Modern PKI practice puts identity in SAN, not CN. Open Banking profiles also tend to rely on more structured certificate attributes than a bare CN string. If SBS keeps CN for the sandbox, that is workable, but as a production contract it is brittle.

2. **The XFCC trust model is still too loose for an Accepted ADR.** ADR 0031 explicitly states that in `proxy` mode anyone with network access to the backend listener can forge XFCC until Part 9 lands (`0031`, Consequences, “Proxy-mode trust gap until Part 9”). That is not just an operational note; it means the production path described in the ADR is not secure unless other controls are already in place. For an Accepted contract, I would expect a fail-closed requirement such as “proxy mode is forbidden unless trusted proxy CIDRs / mTLS backend / header scrubbing are configured”.

3. **Thumbprint encoding is likely wrong for RFC 8705 interoperability.** ADR 0031 defines `Hash=<hex-sha256>` in XFCC and ADR 0032 stores `cnf.x5t#S256` as “SHA-256 thumbprint” without stating base64url encoding. RFC 8705 uses the JWK thumbprint-style member name `x5t#S256`, which is conventionally base64url encoded SHA-256, not lowercase hex. If the token claim uses hex, it will be a private contract, not RFC-shaped. That should be made explicit or corrected.

4. **Token endpoint client authentication is underspecified.** ADR 0032 says the token endpoint uses Basic auth with `client_id:client_secret` and also requires mTLS (`0032`, Decision, “Token endpoint”). It does not say how `client_id` is bound to the institution resolved from the cert, whether one institution may have multiple clients, how secrets are stored, rotated, disabled, or audited, or what happens on mismatch between Basic credentials and mTLS identity. Those are load-bearing parts of the contract.

5. **Rate-limit headers on all authenticated 4xx/5xx responses need care.** ADR 0033 says the four headers are emitted on every authenticated response, including errors (`0033`, Decision, “Headers on every response”). That is fine in principle, but the middleware placement described earlier says rate limiting runs “inside the OAuth token validation” (`0033`, Decision, “Middleware placement”). If auth fails before institution resolution, the contract cannot consistently emit per-institution rate headers. The document should distinguish:
   - authenticated and institution-resolved responses;
   - token-endpoint responses keyed by cert/CN;
   - unauthenticated failures with no headers.

6. **The batch endpoint materially weakens the stated protection goal.** ADR 0033 acknowledges that `POST /v1/batches` can carry unbounded complaints and so bypass the effective ingestion limit (`0033`, Consequences, “Batch upload bypasses…”). That is a significant policy hole, not a minor future enhancement, if downstream protection is one reason for rate limiting.

## Disagreements with primary review

I would push harder than a typical primary review on these points:

1. **“Known future hardening” is not enough for proxy mode.**
   If the primary review accepted the XFCC path as adequate because the trust gap is documented, I disagree. The ADR currently accepts a mode where header forgery equals institution impersonation (`0031`, Consequences). For a regulator-facing platform, that should be blocked by contract now, not left as an operator warning.

2. **CN-only identity should not pass unchallenged.**
   If the primary review treated CN-as-identifier as acceptable because Open Banking UK is cited, I disagree with that reading. Even if a comparator once used CN-based conventions, current industry practice is to avoid relying on CN alone. Comparators to look at: CAB Forum Baseline Requirements, SPIFFE identities, and modern service mesh / gateway products such as Envoy and Istio, which carry verified SAN/URI identity rather than CN parsing.

3. **HS256 in sandbox is not the main concern; key semantics are.**
   The ADR anticipates reviewers flagging “signing key on disk” (`0032`, Consequences). That is not my main objection. For sandbox, a file-backed key is acceptable. The bigger issue is that **HS256 means the issuer and verifier share the same secret**, which complicates any future split between auth server and resource server. If production is expected to move to RS256, the ADR should state that verifiers must already be written against a `kid` + algorithm policy and must reject algorithm confusion. The main risk is migration correctness, not the presence of a sandbox file.

4. **The rate-limit comparator is only partial.**
   Stripe is a reasonable comparator for header shape and token bucket behaviour, but not for public-sector institution onboarding or proportional treatment. If the primary review accepted the precedent section as sufficient, I would say it is thin. There is no comparator here for supervisory or regulator APIs with named institutions and tier-based quotas. The policy may still be fine, but the precedent claim is narrower than the text suggests.

## Risks not flagged elsewhere

1. **Replay protection gaps across the three ADRs**
   ADR 0031 and 0032 refer to HMAC in ADR 0027, but these texts do not state clearly whether the token endpoint itself requires HMAC signing, whether GET requests do, and what the freshness window is. If the protected business endpoints rely on HMAC for replay resistance, omission or inconsistency at specific endpoints will create a gap. This matters most for:
   - `POST /v1/oauth/token`;
   - `POST /v1/complaints`;
   - `POST /v1/batches`;
   - `PATCH /v1/complaints/{id}/status`.

2. **No clear certificate-to-client mapping model**
   ADR 0031 maps CN to `institution_id` through `institution_certificates`. ADR 0032 separately uses `client_id:client_secret`. There is no stated model tying these together:
   - Is `client_id` unique per institution?
   - Can one institution have multiple client IDs?
   - Can one certificate be used by multiple client IDs?
   - What error code applies on mismatch?

   Without that, operators cannot onboard institutions consistently and developers may make hidden assumptions in code.

3. **Revocation semantics are incomplete**
   ADR 0031 discusses certificate revocation but ADR 0032 says OAuth token revocation is by client_secret rotation and server-side token revocation is unnecessary (`0032`, Decision, “No refresh, no introspection, no revocation list”). That leaves an important gap: if a certificate is revoked, are already-issued tokens bound to that certificate still valid until expiry? The intended answer is probably “no”, because each request recomputes the thumbprint from the current connection, but the ADR should say that a revoked cert fails at the mTLS layer before token validation. This matters for incident response.

4. **Error semantics may conflict with TLS reality**
   ADR 0031 assigns application-level 401/403 codes such as `CERT_REQUIRED`, `CERT_INVALID`, and `CERT_EXPIRED`. In `direct` mode, many of these failures will happen during TLS handshake, before HTTP exists. In `proxy` mode, they may be generated by the proxy, not the app. Unless the reverse proxy is configured to translate TLS auth failures into the same RFC 9457 body and codes, the stated “stable error codes” are not actually stable across modes.

5. **Unicode / canonicalisation risk in CN parsing**
   The contract treats CN as a simple institution identifier like `BANCO_DEMO_001`. The ADR does not say whether CN comparison is case-sensitive, ASCII-only, normalised, or restricted by issuance policy. If production certificates permit broader character sets, string comparison and logging can become ambiguous. At minimum, the cert profile should restrict institution CNs to a narrow character set if CN continues to be used.

6. **Rate limiting keyed by institution may hide abuse by shared infrastructure**
   ADR 0033 correctly says proxy-only limits do not know the institution. But a pure per-institution limit also misses concentration risk from a broken or hostile client source. In practice, gateways such as Envoy, Kong, and Apigee commonly combine:
   - coarse per-IP / per-connection limits at the edge;
   - finer business limits keyed by client identity.

   The ADR mentions an outer DoS limit in Consequences, but not as a contract requirement. That should be stronger.

7. **Request cost is not aligned to endpoint cost**
   ADR 0033 explicitly chooses not to use per-endpoint or compute-unit limits. That is acceptable for a first cut, but here the mismatch is large:
   - `GET /v1/status/*` is cheap;
   - `POST /v1/batches` can be very expensive;
   - `POST /v1/oauth/token` has crypto and secret verification cost.

   One flat “requests per minute” figure can therefore misstate fair use and system protection.

8. **No stated clock-skew tolerance**
   ADR 0032 enforces `exp` and uses `iat`, but does not state allowed clock skew. If verifiers use zero tolerance, clients near expiry will see hard-to-diagnose failures. Industry practice is a small tolerance, usually 30–120 seconds, documented and tested.

9. **No `nbf` or `jti` claim decision**
   For 15-minute client_credentials tokens, `jti` is not mandatory, but the ADR should explicitly say whether replay tracking is intentionally omitted. Without that, later teams may assume there is per-token uniqueness or revocation support when there is not.

10. **Observability contract is missing from all three ADRs**
    Given the stated platform principle that observability is first-class, these ADRs should say what must be logged and measured:
    - auth failure counters by code;
    - certificate subject / institution resolution failures;
    - token issuance success/failure by client_id and institution_id;
    - rate-limit decisions and bucket saturation;
    - clear redaction rules for certs, secrets, and bearer tokens.

    Right now the ADRs define user-visible behaviour but not operator-visible behaviour.

## Recommended actions

1. **Tighten proxy-mode acceptance criteria in ADR 0031**
   - State that `proxy` mode is invalid unless all of the following are configured:
     - backend listener reachable only from trusted proxy addresses or loopback;
     - inbound `X-Forwarded-Client-Cert` stripped from untrusted requests at the proxy;
     - backend-to-proxy authentication, preferably mTLS;
     - explicit trusted-proxy configuration in the app.
   - If those controls are absent, startup should fail closed rather than warn.

2. **Change the identity contract away from CN-only, or narrow it explicitly**
   - Preferred: use SAN/URI or another structured identity field for production, with CN retained only for sandbox compatibility.
   - If CN must remain, define an issuance policy:
     - ASCII uppercase letters, digits, underscore only;
     - exact match semantics;
     - maximum length;
     - uniqueness rules.
   - Record why this is acceptable for SBS PKI.

3. **Fix thumbprint encoding language in ADR 0031 and 0032**
   - Decide one canonical encoding for:
     - XFCC `Hash=...`;
     - DB storage;
     - JWT `cnf.x5t#S256`.
   - For RFC 8705 alignment, use base64url for the JWT claim and document any conversion from proxy header or DB representation.
   - Add an explicit test vector.

4. **Add the missing client authentication model to ADR 0032**
   - Define a `oauth_clients` model or equivalent:
     - `client_id`;
     - secret hash, not plaintext;
     - `institution_id`;
     - status/disabled flag;
     - rotation timestamps;
     - audit fields.
   - Specify whether multiple clients per institution are allowed.
   - Add a stable error for “client credentials valid but not bound to presenting institution”.

5. **Clarify error ownership across TLS and HTTP layers**
   - Separate:
     - handshake failures handled by uvicorn / proxy;
     - application-level 401/403 after a verified cert is present.
   - If stable problem codes are required in both modes, require the reverse proxy to emit the same problem+json contract for TLS-auth failures.

6. **Strengthen rate-limit policy before it hardens**
   - Keep the per-institution bucket.
   - Add one of:
     - a separate batch size or batch complaint-count limit;
     - compute-unit charging for expensive endpoints;
     - endpoint-specific weights in the bucket.
   - Otherwise the rate limit does not meaningfully bound ingestion load.

7. **Document clock and token validation policy**
   - Add allowed clock skew.
   - State whether `nbf` is absent by design.
   - State whether `jti` is absent by design and that there is no per-token revocation/introspection in this phase.

8. **Add observability requirements to each ADR**
   - Minimum logs/metrics:
     - mTLS validation result by code and mode (`direct`/`proxy`);
     - institution resolution result;
     - token issuance and verification failures by reason;
     - rate-limit permit/deny counts and Redis errors;
     - correlation/request IDs on all auth failures.
   - Minimum redaction rules:
     - never log bearer token, client secret, raw cert, or full Basic auth header;
     - thumbprint may be logged;
     - subject/CN may be logged if treated as institution identity.

9. **State fail-open/fail-closed behaviour for dependency outages**
   - If Redis is down, does the API reject protected requests or bypass rate limits?
   - If certificate revocation source is stale or unavailable in production, does the proxy reject or continue?
   - If token signing key cannot be loaded, does `/v1/oauth/token` fail closed while resource requests continue?

   These are operationally important and should be explicit.

10. **Add cross-ADR onboarding examples**
    - One worked example from certificate issuance through DB records, client credential issuance, token request, protected API call, and expected logs/errors.
    - This will expose any hidden mismatch between `institution_certificates`, `institutions`, scopes, and token validation.
